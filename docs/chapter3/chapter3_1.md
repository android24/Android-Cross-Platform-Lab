本节先明确 Android 原生基准版本要做到什么程度。后续 Hybrid、React Native、Flutter、KMP 等技术栈都要围绕同一组能力对照，否则最终比较就会变成“各做各的 Demo”。

## 为什么先做原生基准

Android 原生版本承担三类作用：

- 功能基准：确定贯穿项目最小可比较能力。
- 工程基准：确定数据层、页面、原生能力和性能记录的边界。
- 评测基准：给后续技术栈提供同一套比较口径。

它不是课程终点，而是后面所有跨平台方案的参照物。

## P0：最小可比较版本

P0 是本章必须完成的范围。

| 能力 | 要求 | 对照意义 |
| --- | --- | --- |
| 首页/目录页 | 左侧目录，右侧详情，横屏优先 | 对照不同 UI 框架的布局能力 |
| 手册详情页 | 标题、摘要、正文、图片占位、收藏入口 | 对照图文内容展示和滚动体验 |
| 搜索页 | 按标题、摘要或正文搜索，支持空结果 | 对照状态管理和列表性能 |
| 车辆状态页 | 展示电量、续航、胎压、车门、空调和车速 | 对照持续数据订阅和生命周期处理 |
| 原生能力页 | 通知、文件选择或相机至少完成一个 | 对照 Bridge、Native Module、Platform Channel 成本 |
| 性能记录 | 至少填写一次启动或内存记录 | 为第七篇性能比较提供首个样例 |

## P1：完整课程版本

P1 在 P0 基础上补齐常见业务能力：

- 收藏和浏览历史。
- 图片加载和本地缓存。
- 离线模式。
- 深色主题。
- 中文和英文切换。
- 文件、相机、通知三个原生能力。

P1 的目标是让原生版本具备完整课程体验，而不是只停留在最小样本。

## P2：毕业项目增强版本

P2 面向毕业项目和技术选型报告：

- 完整性能测试入口。
- 更清晰的模块边界。
- 可复用 Repository 设计。
- 与 Hybrid、RN、Flutter 或 KMP 混合接入的边界说明。
- 面向企业选型的工程成本记录。

## 阶段验收清单

| 项目 | P0 是否必须 | 说明 |
| --- | --- | --- |
| 可启动应用 | 是 | 启动后进入手册或主导航页面 |
| 共享数据读取 | 是 | 不手写一套只属于原生版本的数据 |
| 目录详情体验 | 是 | 横屏主从布局优先 |
| 搜索 | 是 | 本地搜索即可 |
| 车辆状态 | 是 | 样例数据或定时模拟均可 |
| 原生能力 | 是 | 通知、文件选择、相机任选一项 |
| 性能记录 | 是 | 至少一项，并说明测试方法 |
| 收藏历史 | 否 | P1 阶段补齐 |
| 离线和图片缓存 | 否 | P1 阶段补齐 |
| 多语言和主题 | 否 | P1 阶段补齐 |
