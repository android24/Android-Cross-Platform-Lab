本章对应课程规划中的第一篇：Android 原生基准。

本篇不是单纯介绍 Android API，而是用 Kotlin 与 Jetpack Compose 先实现“跨平台智能座舱电子手册与车辆助手”的原生版本。后续 Web/PWA、Hybrid、React Native、Flutter、KMP 等方案都要和这个原生版本对照。

## 本章定位

Android 原生基准承担三类作用：

- 功能基准：确定贯穿项目最小可比较能力。
- 架构基准：确定页面、数据层、状态管理、缓存、Service 和性能记录的边界。
- 评测基准：给后续跨平台技术栈提供统一比较口径。

原生基准不是为了证明“原生一定最好”，而是为了建立一个足够清楚的参照物：同一业务在 Android 原生中怎样组织，换到跨平台方案后哪些地方会变简单，哪些地方会变复杂。

## 最小完成范围

完成本章后，`native-android/` 至少应达到 P0：

| 能力 | P0 要求 |
| --- | --- |
| 首页/目录页 | 横屏下左侧目录、右侧详情 |
| 手册详情页 | 标题、摘要、正文、图片占位、收藏入口 |
| 搜索页 | 按标题、摘要或正文搜索，支持空结果 |
| 车辆状态页 | 展示电量、续航、胎压、车门、空调和车速 |
| 原生能力页 | 通知、文件选择或相机至少完成一个 |
| 性能记录 | 至少填写一次启动或内存记录 |

P1 再补齐收藏历史、图片缓存、离线模式、深色主题、多语言和完整原生能力。P2 用于毕业项目增强，包括完整性能测试入口、混合接入边界和企业选型报告。

## 和后续章节的关系

后续每一种跨平台方案都要回答同一组问题：

- 目录、详情、搜索这些 UI 在该技术栈中如何实现。
- 数据层和 Repository 是否能复用，是否适合迁移到 KMP。
- 原生能力从跨平台层调用 Android 层时，多了哪些边界。
- 启动、内存、帧率和包体积与原生基准相比有什么差异。
- 调试、依赖、工程配置和团队成本是否发生变化。

因此，本章越清晰，后面的跨平台比较越有说服力。
