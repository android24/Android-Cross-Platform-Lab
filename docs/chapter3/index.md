本章用于补齐课程二的第一条完整样板路径：先用 Android 原生技术实现“跨平台智能座舱电子手册与车辆助手”的 P0 版本，再把它作为后续 Web/PWA、Hybrid、React Native、Flutter、KMP 等技术栈的对照基准。

原生基准不是为了证明“原生一定最好”，而是为了回答三个问题：

- 同一业务在 Android 原生中最自然的工程边界是什么。
- 哪些功能后续进入跨平台方案后会产生桥接、渲染、缓存或调试成本。
- 性能和工程成本比较应该以什么功能范围作为共同口径。

## 本章目标

完成本章后，学习者应能得到一个最小可比较版本：

| 能力 | 要求 | 对照意义 |
| --- | --- | --- |
| 目录与详情 | 横屏下左侧目录、右侧图文说明 | 作为所有 UI 方案的布局基准 |
| 搜索 | 支持标题、摘要、正文关键词搜索 | 比较本地索引、状态管理和列表性能 |
| 车辆状态 | 展示模拟电量、续航、胎压、车门、空调、车速 | 比较持续数据订阅和生命周期管理 |
| 原生能力 | 至少接入通知、文件选择或相机中的一个 | 后续对比 Bridge、Native Module、Platform Channel |
| 性能记录 | 至少记录启动或内存中的一项 | 为第七篇性能评测提供第一份样例 |

## 和前置课程的关系

本章会反复使用 Cross-Platform Internals 中的几个概念：

| 原理概念 | 本章落点 |
| --- | --- |
| 渲染路径 | Compose 状态变化如何驱动 UI 重组和绘制 |
| 线程模型 | Repository、Service、UI 状态之间如何避免阻塞主线程 |
| 原生能力边界 | 通知、文件选择、相机为什么在原生中成本较低 |
| 性能模型 | 冷启动、首屏、内存和滚动帧率如何记录 |
| 工程边界 | 哪些代码应留在 Android 层，哪些可以抽象为共享业务逻辑 |

## 完成本章后的基准结论

学习者完成本章后，需要写出一段不超过 500 字的基准结论，至少回答：

- 原生版本中最顺手的三个点是什么。
- 原生版本中最容易变复杂的两个点是什么。
- 如果换成 Hybrid、RN、Flutter 或 KMP，实现成本最可能增加在哪里。
- 后续跨平台版本必须和原生版本保持一致的 P0 功能有哪些。

这段结论会作为后续技术栈比较的起点。课程二最终不是简单比较“谁代码少”，而是比较同一业务在不同技术边界下的真实成本。
