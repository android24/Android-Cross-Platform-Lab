本章对应课程规划中的第一篇：Android 原生基准。

本篇不是单纯介绍 Android API，而是用 Kotlin 与 Jetpack Compose 先实现“跨平台智能座舱电子手册与车辆助手”的原生版本。后续 Web/PWA、Hybrid、React Native、Flutter、KMP 等方案都要和这个原生版本对照。

## Demo 入口

本章配套 Demo 位于仓库的 [`native-android/`](https://github.com/android24/Android-Cross-Platform-Lab/tree/main/native-android) 目录。当前 Demo 已经提供一个可用的 Android Studio 工程，学习者可以先运行或预览，再按本章各小节逐步把样例数据、状态管理、缓存和性能记录做扎实。

建议先试玩以下路径：

1. 打开 [`native-android/`](https://github.com/android24/Android-Cross-Platform-Lab/tree/main/native-android) 工程，观察横屏下目录和详情的主从布局。
2. 点击不同目录，查看详情页和浏览历史变化。
3. 进入搜索页，输入“胎压”“空调”或 `charging`。
4. 点击收藏按钮，再进入设置页查看状态快照。
5. 进入车辆页，观察模拟车辆数据自动刷新和胎压提醒。
6. 进入原生能力页，尝试文件选择或系统分享。
7. 进入性能页，重置手动记录并执行一遍统一操作路径。

## 本章定位

Android 原生基准承担三类作用：

- 功能基准：确定贯穿项目最小可比较能力。
- 架构基准：确定页面、数据层、状态管理、缓存、Service 和性能记录的边界。
- 评测基准：给后续跨平台技术栈提供统一比较口径。

原生基准不是为了证明“原生一定最好”，而是为了建立一个足够清楚的参照物：同一业务在 Android 原生中怎样组织，换到跨平台方案后哪些地方会变简单，哪些地方会变复杂。

## 学习路径

本章建议按“先跑起来，再接数据，再做状态，最后测性能”的顺序推进：

```text
3.1 创建原生壳工程
  ↓
3.2 建立页面导航和横屏布局
  ↓
3.3 接入统一数据
  ↓
3.4 用 UI State 管理页面变化
  ↓
3.5 做搜索闭环
  ↓
3.6 保存收藏、历史或离线开关
  ↓
3.7 接入车辆状态刷新
  ↓
3.8 记录 Android 原生性能基准
```

学习者不需要等到所有功能都完美后才进入下一节。每节都先完成最小闭环，再把未完成的增强项留给后续迭代。这样可以更早看到一个能运行、能比较、能继续扩展的原生样本。

## 本章实践边界

完成本章时，`native-android/` 应先形成一条可比较的原生样本：能浏览手册、能搜索内容、能展示车辆状态、能接入至少一个原生能力，并能记录一次基础性能数据。收藏、历史、图片缓存、离线模式、深色主题、多语言和完整原生能力可以在后续迭代中逐步补齐。

本章正文只说明教学内容和实现思路。章节完成后的复盘由课程维护过程单独处理，不作为学习正文的一部分。

## 和后续章节的关系

后续每一种跨平台方案都要回答同一组问题：

- 目录、详情、搜索这些 UI 在该技术栈中如何实现。
- 数据层和 Repository 是否能复用，是否适合迁移到 KMP。
- 原生能力从跨平台层调用 Android 层时，多了哪些边界。
- 启动、内存、帧率和包体积与原生基准相比有什么差异。
- 调试、依赖、工程配置和团队成本是否发生变化。

因此，本章越清晰，后面的跨平台比较越有说服力。
